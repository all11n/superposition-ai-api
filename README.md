# Superposition AI

FastAPI-сервис для принятия решений соперником в игре «Суперпозиция»

Проект реализует три уровня алгоритмов, которые получают текущее состояние партии и выбирают одно допустимое действие. После выполнения действия игровым backend состояние обновляется, и при необходимости AI получает следующий запрос.

## Взаимодействие в проекте

Общий цикл взаимодействия:

```text
Spring Boot Backend
        │
        │ текущее состояние партии
        ▼
Superposition AI
        │
        │ одно выбранное действие
        ▼
Spring Boot Backend
        │
        │ применение действия
        ▼
обновлённое состояние
        │
        └──────────────► следующий запрос к AI
````

Такое разделение позволяет независимо изменять алгоритмы принятия решений, не перенося игровую логику из backend в AI-сервис.

## Уровни AI

В проекте реализованы три варианта принятия решений:

### 1. `low`

`LOW` — быстрый эвристический алгоритм, ориентированный на непосредственный эффект действия.

Сначала из текущего состояния формируется набор допустимых действий. Для каждого действия выполняется локальная симуляция: алгоритм оценивает, как изменится состояние кубиков после его применения, не изменяя реальное состояние партии.

Основным критерием является изменение количества правильно установленных кубиков:

```text
изменение своих правильных кубиков
−
изменение правильных кубиков соперника
```

В виде формулы:

```text
score =
(after_correct_own - before_correct_own)
-
(after_correct_opponent - before_correct_opponent)
```
Таким образом, алгоритм учитывает одновременно два эффекта:

* насколько действие приближает собственные кубики AI к целевым состояниям;
* насколько действие ухудшает положение соперника.

Для каждого допустимого действия вычисляется значение `score`, после чего выбирается действие с максимальной оценкой.
Схематично работа `LOW` выглядит следующим образом:

```text
текущее состояние
       │
       ▼
генерация допустимых действий
       │
       ├── действие 1 ──► симуляция ──► score
       ├── действие 2 ──► симуляция ──► score
       ├── действие 3 ──► симуляция ──► score
       │
       ▼
выбор максимального score
       │
       ▼
одно действие
```

Алгоритм не строит дерево будущих состояний и не моделирует несколько последовательных ходов, поэтому он работает быстро и подходит для режима, в котором требуется минимальное время принятия решения.

---

### 2. `mcts`

`MCTS` (`Monte Carlo Tree Search`) используется для более глубокого поиска по пространству возможных игровых решений.
В отличие от `LOW`, алгоритм оценивает действие не только по его непосредственному результату, но и по возможным продолжениям партии после него.
Каждый узел дерева соответствует состоянию игры, а переход из одного узла в другой соответствует одному допустимому действию.

Общая структура:

```text
                     текущее состояние
                            │
              ┌─────────────┼─────────────┐
              │             │             │
          действие 1    действие 2    действие 3
              │             │             │
           состояние      состояние      состояние
              │             │             │
             ...           ...           ...
```

Для построения дерева используется классический цикл MCTS из четырёх этапов.

#### Selection

Начиная с корневого состояния, алгоритм последовательно выбирает дочерние узлы, которые считаются наиболее перспективными.
Для выбора используется статистика, накопленная во время предыдущих симуляций. Таким образом, дерево постепенно концентрирует вычисления на действиях, которые показывают более перспективные результаты, сохраняя при этом возможность исследовать менее посещённые ветви.

#### Expansion

Когда алгоритм достигает состояния, для которого ещё не исследованы все возможные действия, создаётся новый дочерний узел.
Для него выбирается одно допустимое действие и формируется новое состояние игры.
Каждый новый узел поэтому соответствует конкретному переходу:

```text
состояние + действие = новое состояние
```

#### Simulation

После расширения дерева выполняется симуляция дальнейшего развития партии.

На этом этапе алгоритм не продолжает строить дерево до конца партии. Вместо этого выполняется ограниченное моделирование последующих действий.

Во время симуляции учитываются игровые механики, представленные в модели состояния, в том числе:

* изменение состояний кубиков;
* целевые состояния;
* защищённые слоты;
* применённые карты;
* специальные карты;
* дополнительные действия;
* завершение партии.

Для выбора действий во время rollout используется упрощённая политика, позволяющая быстро получить результат большого количества продолжений.

#### Backpropagation

Полученный результат передаётся обратно от конечного состояния к корневому узлу.
Для каждого посещённого узла обновляется накопленная статистика. Благодаря этому следующие итерации MCTS получают информацию о результатах предыдущих симуляций.

Общий цикл:

```text
Selection
    │
    ▼
Expansion
    │
    ▼
Simulation
    │
    ▼
Backpropagation
    │
    └──────────────► следующая итерация
```

### Оценка состояния в MCTS

Если во время симуляции достигается конечное состояние, результат оценивается следующим образом:

```text
победа AI       → +100
победа соперника → -100
```

Для промежуточных состояний используется эвристическая оценка:

```text
score =
3 * correct_own
-
2 * correct_opponent
-
0.02 * moveNumber
```

где:

* `correct_own` — количество правильно установленных кубиков AI;
* `correct_opponent` — количество правильно установленных кубиков соперника;
* `moveNumber` — номер текущего хода.

Таким образом, функция оценки учитывает как положение обоих игроков, так и длину партии, при прочих равных условиях более раннее достижение выгодного состояния получает преимущество.

### Ограничение поиска

Для одного запроса используется ограничение времени поиска до **4.5 секунд**.
MCTS выполняет итерации до окончания доступного времени, дополнительно используется ограничение максимального количества итераций как защитный предел.
По завершении поиска из корневого состояния выбирается одно действие, соответствующее наиболее перспективной исследованной ветви

### 3. `high`

`HIGH` — нейросетевой уровень, основанный на многослойном перцептроне.
В отличие от `LOW`, где решение напрямую вычисляется через простую эвристику, и `MCTS`, где выполняется поиск по дереву состояний, нейросетевой алгоритм использует обученную модель для оценки допустимых действий.

Общая схема:

```text
состояние игры
      │
      ▼
формирование признаков
      │
      ▼
нейросетевая модель
      │
      ▼
оценка допустимых действий
      │
      ▼
выбор действия с максимальной оценкой
```

Для каждого допустимого действия формируется набор числовых признаков, описывающих текущее состояние и само действие

В признаках учитываются:

* состояния кубиков AI и соперника;
* целевые состояния;
* наличие карт на руках;
* защищённые слоты;
* тип выбранного действия;
* выбранная карта;
* целевой слот;
* номер текущего хода.

Перед подачей в нейросеть дискретные игровые значения преобразуются в числовое представление

Архитектура MLP:

```text
Input
  │
  ▼
Dense(128)
  │
 ReLU
  │
  ▼
Dense(64)
  │
 ReLU
  │
  ▼
Dense(1)
  │
  ▼
оценка действия
```

Модель возвращает числовую оценку конкретного допустимого действия. После оценки набора действий выбирается действие с максимальным значением.

Важно, что нейросеть не заменяет генерацию допустимых действий. Сначала определяется, какие действия разрешены текущим состоянием игры, и только после этого нейросетевая модель используется для их оценки.

Схема принятия решения имеет два этапа:

```text
текущее состояние
       │
       ▼
генератор допустимых действий
       │
       ▼
только разрешённые действия
       │
       ▼
нейросетевая оценка каждого действия
       │
       ▼
выбор максимальной оценки
```

Это позволяет отделить игровые ограничения от модели принятия решений, корректность допустимых действий определяется логикой состояния игры, а нейросеть используется непосредственно для выбора между ними

Параметры обученной модели хранятся в файле neural_model_demo.npz

Если подходящие веса отсутствуют или размер входных данных модели не соответствует текущему представлению признаков, используется резервная эвристическая оценка, что позволяет сервису продолжать принимать решения даже при недоступной нейросетевой модели.

## Сравнение алгоритмов

Три уровня отличаются прежде всего глубиной анализа состояния:

| Уровень | Принцип                        |             Глубина анализа |                      Скорость |
| ------- | ------------------------------ | --------------------------: | ----------------------------: |
| `LOW`   | локальная эвристическая оценка |               одно действие |                       высокая |
| `MCTS`  | поиск по дереву и симуляции    | несколько будущих состояний |    ограничена временем поиска |
| `HIGH`  | нейросетевая оценка действий   | зависит от обученной модели | высокая после загрузки модели |

При этом все три алгоритма используют общий принцип взаимодействия с backend:

```text
состояние партии
      │
      ▼
генерация допустимых действий
      │
      ▼
оценка действий выбранным алгоритмом
      │
      ▼
итоговое действие
```

Различается именно способ оценки:

```text
LOW
│
└── непосредственная локальная выгода

MCTS
│
└── результаты симуляций будущих состояний

HIGH
│
└── оценка действия обученной нейросетевой моделью
```

Все алгоритмы работают с одним и тем же представлением состояния и возвращают одно действие в формате API, что позволяет заменять алгоритм принятия решения без изменения схемы взаимодействия между AI-сервисом и игровым backend.

## API

Основной endpoint:

```text
POST /choose-action
```

Пример запроса:

```json
{
  "model": "mcts",
  "aiPlayerId": "player-ai",
  "opponentPlayerId": "player-human",
  "dice": {
    "player-ai": ["ZERO", "PLUS", "ONE", "I"],
    "player-human": ["MINUS", "ZERO", "I_MINUS", "PLUS"]
  },
  "targets": {
    "player-ai": ["ONE", "ZERO", "PLUS", "I"],
    "player-human": ["MINUS", "ONE", "I", "PLUS"]
  },
  "aiHand": [
    {
      "id": "card-uuid-1",
      "type": "PAULI_X"
    },
    {
      "id": "card-uuid-2",
      "type": "HADAMARD"
    }
  ],
  "opponentHand": [],
  "deck": [],
  "discard": [],
  "protected": {
    "player-ai": [false, false, false, false],
    "player-human": [false, false, false, false]
  },
  "appliedCards": {
    "player-ai": [[], [], [], []],
    "player-human": [[], [], [], []]
  },
  "activeRow": null,
  "kroneckerRemainingActions": 0,
  "moveNumber": 12,
  "maxMoves": 80,
  "remainingMoves": 1,
  "currentPlayerId": "player-ai",
  "finished": false
}
```

Пример ответа:

```json
{
  "model": "mcts",
  "action": {
    "type": "PLAY_CARD",
    "playerId": "player-ai",
    "cardId": "card-uuid-1",
    "targetSlotIndex": 2,
    "targetPlayerId": "player-ai"
  },
  "thinkingTimeMs": 4312.57,
  "iterations": 3562
}
```

Основное поле ответа — `action`
Диагностические поля, такие как `thinkingTimeMs` и `iterations`, используются для анализа работы алгоритма
Подробное описание формата запроса, ответа и типов действий находится в `API_DOCUMENTATION.md`.

## Игровое состояние

AI использует следующие компоненты состояния:

* состояния 8 кубиков;
* целевые состояния кубиков;
* карты AI;
* карты соперника;
* колоду и сброс;
* защищённые слоты;
* историю применённых карт;
* номер текущего хода;
* количество оставшихся действий;
* состояние `KRONECKER_MULTIPLICATION`.

Состояния кубиков соответствуют enum `DiceType`:

```text
ZERO
ONE
PLUS
MINUS
I
I_MINUS
```

Типы карт соответствуют `CardType` игрового backend.

Особое состояние `KRONECKER_MULTIPLICATION` передаётся между запросами через:

```json
{
  "activeRow": "player-ai",
  "kroneckerRemainingActions": 1
}
```

## Локальный запуск

Создать виртуальное окружение:

```bash
python -m venv .venv
```

### Windows

```bash
.venv\Scripts\activate
```

```bash
source .venv/bin/activate
```

```bash
pip install -r requirements.txt
```


```text
http://localhost:8000/health
```

### `api_server.py`

HTTP-слой приложения отвечает за:

* описание входного запроса;
* обработку HTTP-запросов;
* передачу состояния в `model_engine`;
* возврат выбранного действия;
* endpoints `/health` и `/models`.

### `model_engine.py`

Основная логика AI, которая содержит:

* представление состояния игры;
* генерацию допустимых действий;
* моделирование действий;
* эвристический алгоритм;
* MCTS;
* нейросетевой уровень;
* преобразование внутренних действий в API DTO

## Ограничения

Текущая реализация рассчитана на мобильную конфигурацию из **8 кубиков: 4 кубика AI и 4 кубика соперника**

Для корректного моделирования отдельных механик необходимо передавать соответствующие данные состояния:

* `appliedCards` — для учёта истории применённых карт;
* `activeRow` и `kroneckerRemainingActions` — для продолжения последовательности `KRONECKER_MULTIPLICATION`;
* `deck` — для более точного моделирования `RESHUFFLE`.

Логика моделирования в AI должна соответствовать правилам, реализованным в Spring Boot backend. При изменении игровых правил соответствующие изменения необходимо отражать в `model_engine.py`
